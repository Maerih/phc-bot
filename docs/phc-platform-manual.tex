\chapter{Introduction}

\section{What this platform is}

The Public Health Colosseum is a global community where students, early
professionals, researchers and practitioners learn, connect and unlock
opportunities in public health. This platform is the infrastructure behind it.

It discovers opportunities from multiple independent sources, normalises them
into a single trustworthy shape, removes duplicates, hides anything past its
deadline, ranks what remains, and delivers the result through two surfaces:

\begin{itemize}
  \item \textbf{WhatsApp} \dash{} 34 commands for members already in the community.
  \item \textbf{Web} \dash{} a public search page requiring no account, no login
        and no app.
\end{itemize}

Both surfaces call the same search engine, so an improvement to ranking or
de-duplication reaches both at once.

The platform covers fourteen opportunity types, including jobs, internships,
scholarships, fellowships, research posts, grants, conferences, training and
events.

\section{What it deliberately does not do}

Stating this plainly is part of the product. A member deciding whether to spend
a week on an application deserves to know what the system is actually claiming.

\begin{itemize}
  \item \textbf{It does not assert that listings are genuine.} Opportunities
        are gathered from third-party sources. Unless a record is explicitly
        marked verified, it has not been independently checked. Every rendered
        result says so and links to the official page.
  \item \textbf{It does not invent missing information.} A field a source did
        not state is stored as null and rendered as ``not stated''. An unknown
        deadline is never shown as ``no deadline'', because those are different
        facts.
  \item \textbf{It does not scrape sites that prohibit it.} See
        Section~\ref{sec:linkedin}.
  \item \textbf{It does not ban or block members automatically.} Moderation is
        designed as \emph{AI recommendation $\rightarrow$ risk score $\rightarrow$
        administrator review}.
\end{itemize}

\section{Current status}

Release 1.0 ``Neo'' is complete, verified and in use. It covers opportunity
discovery across six sources, two delivery surfaces, group administration, an
AI assistant and a live web-search fallback. Later phases are specified in

This manual documents only what exists today. Anything unverified is labelled
as such \dash{} there are two such caveats, and both say so plainly where they

\section{Design principles}

\begin{center}
\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
\textbf{Principle} & \textbf{How it is enforced} \\
\midrule
Provider independence & No business logic imports a vendor SDK. AI sits behind
an interface selected by configuration. \\
Source independence & No code names a specific job board outside its own
connector file. Adding a source touches two files. \\
Transport independence & The search service takes a query and returns scored
results. It has no knowledge of WhatsApp or HTTP. \\
Unknown stays unknown & Unstated fields are null and render as ``not stated''. \\
Graceful degradation & A failing source, missing AI key or thrown handler
degrades one thing, and the user is told. \\
Honest verification & Nothing is presented as verified because it appeared in a
feed. \\
Minimal personal data & A member record is a WhatsApp JID plus whatever the
member chose to share. \\
\bottomrule
\end{tabularx}
\end{center}

\section{Request lifecycle}

\begin{lstlisting}
inbound message
  |
  +- parseInvocation    prefix check; ordinary conversation ignored
  +- touchMember        upsert by JID, refresh lastSeenAt, re-sync admin flag
  +- isBlocked?         drop
  +- adminOnly?         check ADMIN_NUMBERS -> non-admins get "unknown command"
  +- rate limit         persisted token bucket, unless exempt
  |
  +- handler
       +- parseQuery    filters extracted, consumed, removed from free text
       +- react         immediate feedback before the slow part
       +- fanOut        connectors in parallel, each isolated and timed out
       +- applyFilters  hard requirements (type, country, remote, recency)
       +- dedupe        fingerprint pass, then same-org near-duplicate pass
       +- rank          weighted score plus relevance quality gate
       +- setSession    remembered for .next / .prev / .details
       +- reply         rendered page, attribution, degradation warning
       +- logCommand    command name and normalised terms only
\end{lstlisting}

Persistence is deliberately off this path. Discovered opportunities are written
in the background and tracked, so shutdown waits for those writes rather than
aborting them.

\chapter{Installation}

\section{On a server: one command}

To run the bot, log in to a Linux server over SSH as the user who will run it,
and run:

\begin{lstlisting}[language=bash]
curl -fsSL https://raw.githubusercontent.com/Maerih/phc-bot/main/install.sh | bash
\end{lstlisting}

It downloads the bot from GitHub into \texttt{\textasciitilde/phc-bot} and runs
\texttt{./ctl.sh start}, which does the rest in six steps:

\begin{enumerate}
  \item \textbf{Checks the machine}: Linux, CPU type, required tools, disk
        and memory.
  \item \textbf{Gets Docker}: uses Docker if it is installed, otherwise
        downloads a private copy into the bot's folder and runs it as the
        user, with no \texttt{sudo}. Anything only an administrator can
        provide is named, with the exact command to run once.
  \item \textbf{Configures}: on the first run, asks for the admin WhatsApp
        numbers, an optional Gemini key, an optional Tavily key and the
        timezone, and writes \texttt{.env}; on every run, checks it and
        tests the Gemini key with Google.
  \item \textbf{Builds}, only when the code changed, then validates every
        setting with the bot's own rules before anything restarts.
  \item \textbf{Starts the database}, creating it and its tables on the first
        run.
  \item \textbf{Starts the bot}, restarting it only when the code or settings
        changed, offers to start it after a reboot, and shows the WhatsApp QR
        code in the terminal.
\end{enumerate}

\texttt{./ctl.sh start} is safe to run at any time: it changes only what needs
changing. \texttt{./ctl.sh update} pulls the latest version from GitHub and
then does the same, keeping the WhatsApp session, settings and data.
\texttt{./ctl.sh doctor} runs every check without changing anything, and
\texttt{./ctl.sh setup} asks the configuration questions again.
\texttt{docs/DEPLOY-VPS.md} covers the details.

\section{For development}

\begin{lstlisting}[language=bash]
git clone https://github.com/Maerih/phc-bot.git
cd phc-bot
npm install
\end{lstlisting}

\texttt{npm install} pulls roughly 240 packages, most of them the Baileys
dependency tree. Several minutes is normal.

\begin{callout}{Skipped install scripts are expected}
npm may report that install scripts were not run for Baileys, protobufjs and
esbuild. This is harmless \dash{} the platform, its tests and its build all work
correctly without them.
\end{callout}

\section{Verify the toolchain}

\begin{lstlisting}[language=bash]
npm run typecheck    # tsc --noEmit
npm test             # vitest run (75 tests)
npm run build        # tsc -> dist/
\end{lstlisting}

All three should complete without output other than their own banner. The 75
unit tests cover pure logic and require neither a database nor a network, so
they pass on a machine with nothing else set up.

\section{Validation behaviour}

Configuration is parsed and validated \emph{once, at startup}, and then frozen.
Two consequences matter in practice:

\begin{enumerate}
  \item A malformed value stops the process immediately with a message naming
        the offending variable. You find out when you start the service, not
        when a member sends a command that happens to use it.
  \item Changing \texttt{.env} requires a restart. \texttt{npm run dev} reloads
        on source changes but not on configuration changes.
\end{enumerate}

\chapter{Database}

\section{Option A: rootless local server}

The bundled script creates a PostgreSQL cluster owned by your user, on a
non-default port, inside the project directory. It requires no \texttt{sudo}
and never touches a system-wide installation.

\begin{lstlisting}[language=bash]
./scripts/dev-services.sh start     # start, create the database
./scripts/dev-services.sh status
./scripts/dev-services.sh stop
./scripts/dev-services.sh destroy   # stop and delete all local data
\end{lstlisting}

\begin{center}
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Service} & \textbf{Port} & \textbf{Data directory} \\
\midrule
PostgreSQL & 55432 & \texttt{.devservices/postgres} \\
Redis (if installed) & 56379 & \texttt{.devservices} \\
\bottomrule
\end{tabular}
\end{center}

\section{Option B: your own PostgreSQL}

Point \texttt{DATABASE\_URL} at it. No other change is needed.

\begin{callout}{Prefer 127.0.0.1 over localhost}
\texttt{localhost} can resolve to IPv6 \texttt{::1}, which the development
cluster does not bind. If a connection fails with \texttt{localhost}, use
\texttt{127.0.0.1}.
\end{callout}

it to the schema and \texttt{npm run typecheck} fails \dash{} by design.
\end{callout}

\chapter{Integration: WhatsApp}

\section{Ownership model}

The platform owns its own WhatsApp number and its own session. Authentication
state is written to \texttt{WHATSAPP\_AUTH\_DIR} on your machine and never
leaves it. No third-party pairing website is involved, and no session string is
pasted into an environment variable.

\section{Pairing with a QR code}

\begin{enumerate}
  \item Leave \texttt{WHATSAPP\_PAIR\_NUMBER} blank.
  \item Run \texttt{npm run dev}.
  \item A QR code is printed in the terminal.
  \item On the phone: \textbf{WhatsApp $\rightarrow$ Settings $\rightarrow$
        Linked devices $\rightarrow$ Link a device}, then scan.
\end{enumerate}

QR codes rotate roughly every twenty seconds; a fresh one is printed
automatically.

On a server run with \texttt{./ctl.sh} (see \texttt{docs/DEPLOY-VPS.md}),
\texttt{./ctl.sh pair} draws the same QR code in the terminal and closes by
itself once the phone has linked. The QR is never shown on a web page unless
\texttt{PAIRING\_PAGE=on} is set, which is meant only for shared hosting with
no terminal.

\section{Pairing with an eight-character code}

\begin{enumerate}
  \item Set \texttt{WHATSAPP\_PAIR\_NUMBER} to the number in international
        format, digits only, no \texttt{+}.
  \item Run \texttt{npm run dev}.
  \item The code is logged after a few seconds.
  \item On the phone: \textbf{Linked devices $\rightarrow$ Link with phone
        number instead}, then enter it.
\end{enumerate}

\section{Confirming the connection}

\begin{lstlisting}[language=bash]
curl -s http://127.0.0.1:3100/health
# {"status":"ok","whatsapp":"connected","uptimeSeconds":12}
\end{lstlisting}

Session credentials persist across restarts. To unlink, stop the process,
delete \texttt{WHATSAPP\allowbreak\_AUTH\allowbreak\_DIR}, and pair again.

\section{Who can use the bot}

\textbf{Any number, including the bot's own.} Every command is open to every
sender; only commands marked \texttt{adminOnly} check \texttt{ADMIN\_NUMBERS},
and group commands check that chat's own admin list.

That includes the number the bot is paired to. If it is paired to the
operator's phone, the operator can drive it from that phone. Earlier builds
discarded \texttt{fromMe} messages, so the bot connected normally and then
silently ignored its own owner; it now processes them, with a loop guard that
remembers sent message identifiers so an echo of a reply is never re-handled as
input.

Members on newer LID-based WhatsApp accounts are identified by the
phone-number JID that WhatsApp supplies alongside the LID
(\texttt{participantPn} / \texttt{senderPn}). Without that, such a member's
identity could never match \texttt{ADMIN\_NUMBERS}, and administrators on those
accounts would find admin commands silently failing.

\section{Reconnection and automatic re-pairing}

Ordinary disconnections are retried with exponential backoff, capped at sixty
seconds.

A \emph{logged out} session is handled differently. Those credentials are
already dead \dash{} WhatsApp has invalidated them and nothing can revive them
\dash{} so the platform deletes them and starts pairing again by itself. A
fresh QR code, or a pairing code when \texttt{WHATSAPP\_PAIR\_NUMBER} is set,
appears in the logs.

Re-pairing is capped at three attempts per hour. Beyond that the platform stops
and says so, rather than spinning indefinitely generating pairing requests
against WhatsApp. A successful connection resets the counter.

\begin{callout}{Why deleting the credentials is safe}
It only happens on an explicit logout, where the stored session can no longer
authenticate anything. Retaining it would make every subsequent reconnect fail
in exactly the same way, leaving the bot dark until a human noticed.
\end{callout}

\chapter{Integration: opportunity sources}
\label{ch:sources}

\section{How sources work}

Each connector is independently enabled, isolated behind its own twelve-second
timeout, rate-limited to its upstream's stated policy, and cached. One failing
source degrades that source alone, and the user is told the list may be
incomplete.

The result cache's time-to-live \emph{is} the connector's minimum fetch
interval, so a polite source is polled politely without any caller having to
remember to.

This is the highest-signal source available, and it works differently from an

and link directly to the employer's site.

\texttt{oneacrefund}, \texttt{resolvetosavelives}, \texttt{dimagi},
\texttt{givedirectly}.

\begin{lstlisting}[language=bash]

\begin{callout}{The cheapest way to improve results}
Every health employer you add is authoritative, keyless, and ranks above the
aggregators. This has a larger effect on result quality than any other change
available to an administrator.
\end{callout}

\section{Adding a source}

Create a file under \texttt{src/sources/<kind>/} exporting a
\texttt{SourceConnector}:

\begin{lstlisting}[language=Java]
import type { ConnectorMeta, FetchContext, SourceConnector } from '../types.js';
import { buildUrl, getJson } from '../common/http.js';

const meta: ConnectorMeta = {
  slug: 'who-careers',
  name: 'WHO Careers',
  kind: 'API',
  homepageUrl: 'https://careers.who.int',
  supplies: ['JOB', 'INTERNSHIP', 'FELLOWSHIP'],
  minFetchIntervalMinutes: 120,  // honour the upstream's stated limit
  trustScore: 95,                // first-party postings rank higher
  attributionRequired: false,
  unavailableReason: null,       // or a string when a key is missing
};

export const whoConnector: SourceConnector = {
  meta,
  async fetch({ query, signal, log }: FetchContext) {
    const payload = await getJson<Response>(
      buildUrl(ENDPOINT, { q: query.terms }), { signal },
    );
    return payload.items.map((item) => ({ title: item.title /* ... */ }));
  },
};
\end{lstlisting}

Then register it in \texttt{ALL\_CONNECTORS} in
\texttt{src/sources/registry.ts} and add the slug to
\texttt{SOURCES\_ENABLED}.

A connector returns raw records and maps only what its upstream actually said.
It never classifies, de-duplicates or formats \dash{} normalisation does that
identically for every source. Always use \texttt{getJson} rather than
\texttt{fetch} directly, so the connector inherits timeouts, retry policy, the
response-size ceiling and the identifying user agent.

Set \texttt{unavailableReason} when a key or registration is missing: the
connector then stays registered and explains itself instead of being silently
absent.

\chapter{Integration: AI providers}
\label{ch:ai}

\section{What AI is used for}

Two features depend on a model:

\begin{itemize}
  \item \texttt{.ask} \dash{} general public-health question answering.
  \item The \textbf{opportunity web fallback} \dash{} when every configured
        source returns nothing, the platform searches the live web and extracts
        real opportunities from the results (Chapter~\ref{ch:websearch}).
\end{itemize}

Everything else \dash{} search, filtering, classification, de-duplication,
ranking, group administration \dash{} works with no provider at all.
Rule-based classification is the permanent floor, not a placeholder, so a
missing, failing or unbilled provider never degrades the platform.

\section{Gemini \dash{} the default}

Google AI Studio issues a \textbf{free} API key with a usable free tier. That
is why it is the default: the assistant and the fallback both work without a
billing account.

\begin{lstlisting}[language=envfile]
AI_PROVIDER=gemini
GEMINI_API_KEY=your-key-here
GEMINI_MODEL=gemini-3.8-flash
\end{lstlisting}

Get a key at \url{https://aistudio.google.com/apikey}, then verify it:

\begin{lstlisting}[language=bash]
npm run ai:check
\end{lstlisting}

\begin{callout}{Always run ai:check after changing a key or model}
The two things most likely to be wrong \dash{} an unusable model name and a
key without the right tier \dash{} surface only on a real call. The diagnostic
makes one plain call and one search call and reports exactly which failed.
Finding out in one second beats finding out from a member whose question
silently failed.
\end{callout}

\subsection*{Two Gemini behaviours worth knowing}

\textbf{Models are retired without notice.} \texttt{gemini-2.5-flash} returns
HTTP 404 for accounts created after its deprecation, with the real reason only
in the response body. If \texttt{ai:check} reports the model is unavailable,
list what your key can actually use:

\begin{lstlisting}[language=bash]
curl -s "https://generativelanguage.googleapis.com/v1beta/models?key=$GEMINI_API_KEY" \
  | grep -o '"name": "models/[^"]*"'
\end{lstlisting}

\textbf{Thinking tokens come out of the output budget.} Gemini's flash models
reason before answering, and that reasoning is charged against
\texttt{maxOutputTokens}. A small budget is consumed entirely by thinking and
the call returns a valid response with no text \dash{} indistinguishable from a
failure. The provider enforces a floor of 1024 tokens so this cannot happen.

\section{Anthropic}

Paid, and higher quality for difficult reasoning.

\begin{lstlisting}[language=envfile]
AI_PROVIDER=anthropic
ANTHROPIC_API_KEY=sk-ant-...
ANTHROPIC_MODEL=claude-opus-5
\end{lstlisting}

\begin{callout}{A consumer subscription is not API access}
Anthropic API access is a separate paid product. A consumer Claude Pro or Max
subscription does \textbf{not} include an API key and does \textbf{not} grant
API access. Nor can the credentials of a Claude desktop or CLI session be
repurposed to run a service: they are scoped to that application and expire
with it. Obtain a key from the Anthropic Console
(\url{https://console.anthropic.com/}); it is billed per token, independently
of any chat subscription.
\end{callout}

Indicative rates per million tokens: Claude Opus 5 \$5 in / \$25 out, Claude
Sonnet 5 \$2 / \$10, Claude Haiku 4.5 \$1 / \$5.

\section{OpenAI}

\texttt{AI\_PROVIDER=openai} is accepted by configuration but the provider is
not implemented. It logs a clear warning and leaves AI disabled, rather than
failing obscurely at the first question.

\section{Switching providers}

Two lines in \texttt{.env}. Only
\texttt{src/ai/gemini/provider.ts} and \texttt{src/ai/anthropic/provider.ts}
import a vendor SDK; every other file depends on the \texttt{AiProvider}
interface. No command, service or test changes when the provider does.

\section{Guardrails}

Each is covered by a test.

\begin{itemize}
  \item \textbf{No individual medical advice.} A public-health community
        attracts clinical questions. The assistant answers general knowledge
        and declines to advise on any individual's care.
  \item \textbf{No invented opportunities.} It will not fabricate a
        scholarship, deadline, link or organisation. A model guessing a
        deadline costs a member a real application.
  \item \textbf{Member text is data}, wrapped as a quoted question, never
        treated as instructions.
  \item \textbf{A separate budget guard} \dash{} 15 questions per member per
        hour, independent of the general rate limit, so one person cannot
        spend the community's tokens.
  \item \textbf{Errors never leak internals.} Provider messages may name a key
        or an endpoint; the member-facing text never repeats them.
  \item \textbf{Transient failures are retried.} Gemini returns HTTP 503
        ``high demand'' often enough that a single attempt makes the feature
        look broken. Retryable failures get three attempts with backoff;
        an authentication error or a bad model name fails immediately.
\end{itemize}

\section{The .ask command}

One command, not nine. Separate \texttt{.gpt}, \texttt{.claude} and
\texttt{.gemini} commands would differ only in which company bills the
operator, and would hard-code vendor choice into the command surface \dash{}
precisely what this layer exists to avoid. Which model answers is an operator
decision in \texttt{.env}; a member does not need to know.

\chapter{Integration: web search}
\label{ch:websearch}

\section{Why search is separate from the model}

The fallback originally used the model's own built-in search \dash{}
Anthropic's server-side tool, Google's Search grounding. Both turned out to be
\textbf{paid} features. On a free Gemini key, grounded search returns HTTP 429
\texttt{RESOURCE\_EXHAUSTED} on every call while plain generation works
perfectly well.

So the two were separated. Any search backend can supply the pages; any model
can read them:

\begin{lstlisting}
  web search backend  ->  real URLs + snippets  ->  model extracts  ->  opportunities
       (free)                                         (free tier)
\end{lstlisting}

This also makes the model's job narrower and more honest. It no longer searches
or recalls; it extracts from numbered results it was handed, and every URL it
reports can be checked against that list.

\section{How the fallback behaves}

\begin{itemize}
  \item \textbf{Only on zero results.} It never runs when the sources already
        answered, so a normal search costs nothing.
  \item \textbf{Results go through the same pipeline} \dash{} normalised,
        filtered, de-duplicated, ranked \dash{} so they render identically.
  \item \textbf{Marked \texttt{AI\_ASSISTED}}, and the reply says plainly that
        these came from a web search and are not verified.
  \item \textbf{Every entry must carry a real URL} copied from the search
        results. Entries without one are discarded: a lead a member cannot
        click through to verify looks actionable and is not.
  \item \textbf{No invented posting dates.} The model has no reliable one, and
        guessing would corrupt both the recency filter and the ranking.
  \item \textbf{Charged against the member's AI budget} \dash{} the same
        15/hour guard \texttt{.ask} uses.
\end{itemize}

\subsection*{Filtering is deliberately lenient here}

Fallback results are filtered with \texttt{treatUnknownAsMatch}, and the
reason matters. Web pages rarely state an ISO country code, and such a result
never carries a posting date. Applying the strict source filters discarded
every opportunity the fallback found \dash{} two genuine Kenyan scholarships,
thrown away for lacking fields a web page does not have.

Leniency applies to \emph{unknowns only}. A stated country that does not match
is still rejected, an expired deadline is still rejected, and an explicit
remote requirement is still enforced. Five regression tests pin that
distinction.

\section{Group management}

Admin-only. Authorisation is checked against the \emph{group's} own admin list
on every call, never inferred from the command name. Participant actions
additionally require the bot itself to be an admin, and it refuses to act on
itself \dash{} removing or demoting itself would leave the group unmanaged with
no way back.

Three design decisions are worth knowing:

\begin{itemize}
  \item \textbf{Targets come from real WhatsApp mentions}, read from the
        message's context information, not from parsing text that looks like
        \texttt{@2547...}. The visible handle is only a label, so trusting it
        would let anyone forge a target.
  \item \textbf{Warnings are an append-only log}, not a counter. Clearing them
        deactivates rather than deletes, so an administrator asked why a member
        was removed can answer with evidence.
  \item \textbf{Nobody is removed automatically unless an administrator
        chose it}, by setting a moderation rule to \texttt{remove} (see
        below). Otherwise reaching the warning limit only tells an
        administrator, who decides.
\end{itemize}

\section{Moderation}

The bot reads every message in a group and enforces that group's rules.
\textbf{Group admins, platform administrators and the bot itself are never
moderated.} Deleting and removing need the bot to be a group admin; without
that it can only warn, and says so once an hour rather than on every message.

\texttt{.antilink allow <domain>} & Never touch links to a domain, such as

\bottomrule
\end{tabularx}

Each \texttt{<action>} is one of:

\begin{itemize}
  \item \texttt{warn} \dash{} warn the sender;
  \item \texttt{delete} \dash{} delete the message and warn (\texttt{on} means
        this);
  \item \texttt{remove} \dash{} delete, warn, and remove the sender at the
        warning limit;
  \item \texttt{off}.
\end{itemize}

How it behaves:

\begin{itemize}
  \item \textbf{Tuned for an opportunities community.} Posts that mention
        scholarships, vacancies, deadlines or stipends get the benefit of the
        doubt, so an application link or a stipend amount alone never counts
        as an advert. \texttt{.mod test} shows the score and the signals behind
        it before a rule is turned on.
  \item \textbf{One offence per minute.} A burst of rule-breaking earns one
        warning per rule per minute, while every offending message is still
        deleted, so one flood does not use up all of a member's warnings and
        the bot never floods the group with its own notices.
  \item \textbf{The AI is a second opinion, never the first.} Only posts the
        rules already find suspicious reach it, only in groups that turned it
        on, within 60 reviews an hour. An AI error leaves the post alone.
  \item \textbf{Either identity works.} WhatsApp lists members of some groups
        by an anonymous id rather than their number. Admin checks, silences
        and warnings match members by both.
\end{itemize}

Settings live in the database and take effect on the next message. The tables
are added automatically the first time the new version starts.

\section{Welcome messages}

\texttt{.welcome on} greets everyone who joins a group: added by an admin,
through an invite link, by an approved request, or from the community. In a
custom message set with \texttt{.welcome set}, \texttt{\{name\}} tags the
newcomers and \texttt{\{group\}} is replaced with the group's name; without
one, a standard message introduces the community and points to
\texttt{.menu}. \texttt{.welcome test} previews it, tagging the admin who
asked, and \texttt{.welcome reset} returns to the standard message.

\begin{itemize}
  \item \textbf{One welcome per wave.} People who join within a few seconds of
        each other are welcomed in a single message tagging all of them (up to
        twenty, then ``and $N$ others''), and a group gets at most one welcome
        a minute. A shared invite link never turns the bot into a flood.
  \item \textbf{No late welcomes.} Joins that happened while the bot was
        offline for more than ten minutes are skipped.
  \item \textbf{The bot must be able to post.} In a group closed to admins
        (\texttt{.close}), make it an admin.
\end{itemize}

\section{Locations}

Several locations can be given at once, separated by commas or spaces:

\begin{lstlisting}
.job public health nairobi, kisumu
.job public health nairobi, kampala
.scholarships kenya, uganda, tanzania
\end{lstlisting}

Countries are matched as \textbf{OR}. Named cities additionally give a ranking
boost rather than acting as a hard filter: someone asking for Nairobi still
sees a listing that only says ``Kenya'', just below the ones that say Nairobi.

\begin{callout}{Why this is a list and not one value}
The query originally held a single country, resolved from the whole location
string. The moment two places were named it resolved to nothing and
\emph{silently dropped the location filter altogether}, so
\texttt{nairobi, kampala} quietly searched the entire world. A list makes the
failure impossible.
\end{callout}

\chapter{The opportunity pipeline}

\section{Normalisation}

Every source passes through one funnel, so storage, search, ranking and
rendering only ever see one shape. Descriptions are stripped of HTML, with
\texttt{<script>} and \texttt{<style>} bodies removed first. URLs are validated:
only absolute \texttt{http} and \texttt{https} are accepted, so
\texttt{javascript:}, \texttt{data:} and \texttt{file:} never reach a user.
Dates outside the years 2000 to 2100 are rejected as placeholders.

\begin{callout}{Entity-encoded HTML}
Some sources deliver HTML that is itself entity-encoded. Stripping tags before
decoding leaves markup visible as text; decoding before stripping would turn a
literal ``a \&lt; b \&gt; c'' into deleted content. The implementation strips,
decodes, and re-strips only when the result genuinely looks like markup.
\end{callout}

\section{Classification}

Rule-based, running with or without an AI provider. Each classifier reads only
the text where its signal actually lives \dash{} pointing all of them at the
full description produced nonsense, such as a vacancy mentioning ``present at
international conferences'' being typed as a conference.

\begin{center}
\begin{tabularx}{\textwidth}{@{}llX@{}}
\toprule
\textbf{Classifier} & \textbf{Reads} & \textbf{Rationale} \\
\midrule
Type & title, tags & These name what a posting \emph{is}. \\
Categories & title and tags (authoritative); body requires two or more matches
& One passing mention of ``mental health'' in a benefits list is not a subject
signal. \\
Experience & title, tags & ``Senior stakeholders'' in a body is not a seniority
signal. \\
Education & title, body & Qualifications live in the requirements section. \\
Remote & title, location, body & Remote arrangements are often stated only in
prose. \\
Country & title, location & Resolved only when exactly one country is named. \\
\bottomrule
\end{tabularx}
\end{center}

\section{De-duplication}

Two passes. First, an exact content fingerprint over canonical title,
organisation and type. When the organisation is unknown, the source slug is
mixed in, so two unrelated employers who both omitted their name do not collapse
into one record.

Second, near-duplicates within the same organisation and type: one title being
the other plus a qualifier such as ``(Remote)'' or a duty station. Where the
organisation is unknown, no merging occurs \dash{} two employers can advertise
the same title, and wrongly hiding one costs a member a real opportunity.

The surviving copy is chosen by source trust first, then completeness.

\begin{center}
\begin{tabular}{@{}lr@{}}
\toprule
\textbf{Match} & \textbf{Score} \\
\midrule
Phrase in title & 1.00 \\
All terms in title & 0.90 \\
Phrase in tags & 0.75 \\

ignore or loosely honour their own search parameter, so without a gate they
flood the list. Fewer, truer results is the correct trade for a community where
a bad lead costs someone a real application.

\section{Verification lifecycle}

\begin{lstlisting}
DISCOVERED --> PENDING_REVIEW --> VERIFIED --> PUBLISHED --> EXPIRED
                     \--------------> REJECTED
\end{lstlisting}

Everything enters as DISCOVERED and UNVERIFIED. Promotion is a separate,
reviewed step, never a side effect of ingestion. The upsert path deliberately
does not write status, verification status, verification time or review notes:
those record human decisions, and an automated synchronisation overwriting them
would silently re-approve content behind an administrator's back.

\chapter{Security and privacy}

\begin{itemize}
  \item \textbf{Secrets only in the environment.} No key is committed;
        \texttt{.env} and \texttt{auth/} are git-ignored.
  \item \textbf{Minimal personal data.} A member record holds a WhatsApp JID
        plus whatever the member chose to provide. No push names, profile
        photographs or contact-book entries are copied.
  \item \textbf{No personal data in logs.} JIDs are redacted to the form
        \texttt{254***060@s.whatsapp.net}. Raw message text is never logged;
        only the resolved command name is.
  \item \textbf{Anonymous HTTP surface.} \texttt{/api/status} exposes no phone
        number or member identifier.
  \item \textbf{Administrator authorisation} is checked against
        \texttt{ADMIN\_NUMBERS} on the verified sender, before a handler runs.
        Administrator commands return the unknown-command reply to
        non-administrators, so their existence is not confirmed.
  \item \textbf{Persisted rate limiting} per member, so restarting cannot reset
        a flood. Public HTTP endpoints are limited per IP.
  \item \textbf{URL validation and HTML sanitisation} on everything originating
        from a source.
  \item \textbf{No remote code and no remote control.} The platform never
        downloads code at runtime and never takes instructions from a remote
        feed. Everything it runs is in the repository and reviewable.
  \item \textbf{Failure isolation.} A failing source, a thrown handler or an
        unhandled rejection cannot take the service down.
\end{itemize}

\chapter{Development}

\section{Adding a command}

Create a file under \texttt{src/commands/<category>/}:

\begin{lstlisting}[language=Java]
import type { Command } from '../types.js';

export const profileCommand: Command = {
  name: 'profile',
  aliases: ['me'],
  category: 'members',
  summary: 'View or edit your opportunity profile',
  usage: '.profile',
  examples: ['.profile'],
  // adminOnly: true,            // authorised against ADMIN_NUMBERS
  // exemptFromRateLimit: true,  // only for trivial commands
  async handler(context) {
    await context.reply(`Country: ${context.member.country ?? 'not set'}`);
  },
};
\end{lstlisting}

Then import and list it in \texttt{src/commands/registry.ts}. That is all:
\texttt{.help} is generated from the registry, so documentation cannot drift,
and name or alias collisions throw at startup rather than silently shadowing.

The context provides \texttt{reply}, \texttt{react}, \texttt{args},
\texttt{argv}, \texttt{member}, \texttt{isAdmin}, \texttt{log} and session
accessors. A handler never touches the WhatsApp socket, so it is unit-testable
with no connection.

For a search-backed command, delegate to the shared pipeline:

\begin{lstlisting}[language=Java]
import { runSearch } from '../opportunities/run-search.js';

async handler(context) {
  await runSearch(context, {
    forcedTypes: ['SCHOLARSHIP'],
    commandLabel: '.scholarships',
  });
}
\end{lstlisting}

\chapter{Troubleshooting}

\section*{Cannot reach the database}

\begin{lstlisting}[language=bash]
./scripts/dev-services.sh start
npm run db:push
./scripts/dev-services.sh status
\end{lstlisting}

If \texttt{localhost} fails, use \texttt{127.0.0.1}: \texttt{localhost} can
resolve to IPv6, which the development cluster does not bind.

\section*{Invalid environment configuration}

The message names each offending variable. Common causes: \texttt{DATABASE\_URL}
missing or not a URL; \texttt{ADMIN\_NUMBERS} or
\texttt{WHATSAPP\_PAIR\_NUMBER} containing \texttt{+}, spaces or dashes
(digits only).

\section*{WhatsApp will not connect}

\begin{center}
\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
\textbf{Symptom} & \textbf{Cause and remedy} \\
\midrule
No QR code appears & \texttt{WHATSAPP\_PAIR\_NUMBER} is set. Blank it for QR
mode. \\
QR expires & They rotate every twenty seconds; a new one is printed
automatically. \\
``Session logged out'' & The account unlinked this device. Stop, delete
\texttt{WHATSAPP\_AUTH\_DIR}, pair again. Not retried by design. \\
Connects then drops & Another bot is using the same number. Give the platform
its own. \\
Pairing code rejected & Digits only, international format, no \texttt{+}. \\
\bottomrule
\end{tabularx}
\end{center}

\section*{Few or no results}

A search returning nothing is usually a source-coverage gap, not a defect.
Check \texttt{.sources} or \texttt{/api/sources} to see what was actually
searched. The aggregators carry little public-health or African content;
result quality comes from employer career boards and ReliefWeb. See
Chapter~\ref{ch:sources}.

\section*{A source keeps failing}

Failures are logged at warning level because an unreachable upstream is
operational noise, not a platform fault. Searches continue with the remaining
sources and the reply states that the list may be incomplete. Do not lower a
connector's minimum fetch interval below the upstream's stated policy;
Remotive blocks excessive requests.

\section*{Port already in use}

\begin{lstlisting}[language=bash]
ss -ltnp | grep 3100
\end{lstlisting}

Change \texttt{PORT}, or stop the process holding it. Note that a development
server started with \texttt{tsx} does not match a process search for
\texttt{dist/index.js}.

\section*{db:push fails with constraint errors on PostgreSQL 18}

PostgreSQL 18 gives NOT NULL constraints real names
(\texttt{members\_id\_not\_null}). drizzle-kit 0.30 does not recognise them, so
its diff tries to \texttt{DROP} them and fails with \texttt{42P16} on any
constraint backing a primary key \dash{} possibly after having already created
new tables.

Apply schema changes with explicit SQL instead:

\begin{lstlisting}[language=bash]
psql "$DATABASE_URL" -f drizzle/0001_group_moderation.sql
\end{lstlisting}

Migrations in \texttt{drizzle/} are written to be idempotent
(\texttt{IF NOT EXISTS}), so re-running one is safe. On PostgreSQL 17 or
earlier, \texttt{db:push} works normally.

\section*{db:push cannot resolve a module}

\texttt{drizzle-kit} bundles the schema as CommonJS and cannot resolve a
\texttt{.js} specifier onto a \texttt{.ts} file. The schema therefore declares
enum values directly and imports only types, guarded by a compile-time
assertion. If you add a value to the domain, add it to the schema too;
\texttt{npm run typecheck} will tell you if you forget.

\begin{callout}{Stored opportunities are not yet searchable}
Search queries the live sources on every request; the database is written to
but never read from for search. Accumulated opportunities are therefore a
record, not an index. Database-first search is the first item of the next
phase, and it is what makes the store pay for itself.
\end{callout}

\begin{callout}{Multi-tenancy is a sequencing decision, not a later feature}
If the product is to become multi-tenant software-as-a-service, a tenant
identifier must be added to every table \emph{before} real organisations and
real data exist. While the database holds only disposable records the migration
is nearly free; after the first paying community is onboarded it becomes a
painful backfill with downtime. The search engine itself is unaffected.
\end{callout}
